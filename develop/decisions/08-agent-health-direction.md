# Decision 08 — 에이전트 헬스: 측정기에서 건강 관리로

Date 2026-10-24. Status: **proposed (아이디어)**. 결정 전. 아래 "첫 단계"를 해 보고 채택 여부를 정한다.
표기: confirmed = 로컬 파일·로그·소스로 확인 / hypothesis = 추론, 확인 방법 함께 / unknown = 모름.

## 한 줄

ctxmeter를 "세션 시작 비용 측정기"에서 **멀티 에이전트 사용자를 위한 건강 앱**으로 넓힌다.
사람 대신 에이전트 셋업의 체성분·활동량·칼로리 환산을 기록하고, 주간 리포트와 코칭, 직접 eval까지 한다.

## 왜 — 실제로 겪은 문제 (2026-10-23 실측, confirmed)

- 매달 Claude Code·Codex만 한도가 바닥나고 Kiro는 약 30% 남는다.
- 원인은 "Kiro에 일을 덜 줘서"가 아니라 **조율자 세션이 평균 25만 토큰 컨텍스트로 도구를 수천 번 직접 호출**하는 것이었다.
  - Claude: 30일 사용량의 69%가 한 프로젝트, 세션 3개가 컨텍스트 토큰 1.26B 중 1.18B.
  - Codex(Plus): 785M 중 세션 하나가 661M. 25일째 같은 세션.
- 위임 경로를 고친 첫날 새 누수가 나왔다: Codex가 작업자를 기다리며 `sleep 50초` → 완료 파일 확인을 반복 → **입력 토큰의 37%**.
- Codex 압축 후에도 컨텍스트가 9.5만 아래로 안 내려갔다. 압축 기록에 **사용자가 붙인 이미지 30장이 계속 보존**돼 모든 요청마다 다시 읽히고 있었다.
- 이 셋 다 "토큰이 얼마 나갔나"를 세는 도구로는 안 보인다. 흐름(누가 누구를 기다리나, 무엇이 압축을 살아남나)을 봐야 보인다.

## 건강 앱 비유 → 기능

| 건강 앱 | 에이전트 헬스 | 지금 상태 |
|---|---|---|
| 체성분 | 세션 시작 비용: 규칙·스킬·steering·hook·MCP가 매 세션 얼마나 무거운가 | **ctxmeter v0.3.0이 이미 함** (audit·mcp-scan·fix·메뉴바) |
| 활동량 | 턴 수 × 컨텍스트, 도구 호출 분류, 압축 시점·압축 후 바닥 | 프로토타입 있음(아래) |
| 칼로리 환산 | **토큰 → 한도 %·크레딧 환율**, 회사·플랜·모델·effort별. 같은 플랜에서 환율이 바뀌면 감지 | 없음. 시장에도 없음 |
| 운동 기록 | 위임 작업 장부: 누가 누구에게, 얼마나 걸렸나, 성공했나, 다시 시켰나 | `kiro-run` 장부로 시작 |
| 주간 리포트 | 목표 대비 ✅/❌ | 프로토타입 있음 |
| 코칭 | 흐름 진단: 대기 폴링, 이미지 누적, 잘게 쪼갠 위임, 마라톤 세션 → 고칠 것 제시 | 수동으로만 찾음 |
| 건강검진 | **직접 eval**: 설정 변경 전후 A/B를 품질 확인과 함께 | 없음 |

`decisions/01`의 교훈은 그대로 유지한다: 숫자만 보여주면 아무도 안 쓴다. 모든 화면은 "그래서 무엇을 바꿀지"로 끝나야 한다.

## 시장 공백 (2026-10 조사, vault `20_tech/agent-status/2026-10-23-multi-agent-optimization-research.md`)

- 로컬 로그 분석 도구는 많다: tokenol, cc-analyzer, agent-cost, cost-xray, Decant, tokmeter, tycho, tokentab, CodexBar(한도 표시).
  전부 **토큰·달러를 세는** 쪽이다.
- 비어 있는 셋:
  1. **한도 환율 역추적.** 캐시 토큰이 구독 한도에 얼마로 반영되는지 공개 수치가 없다(조사 시점 unknown).
  2. **멀티 에이전트 흐름 진단.** 조율자 부담·대기 낭비·위임 비중·재위임 비율.
  3. **품질 게이트가 있는 설정 A/B.** "Measuring the Wrong Number"(AgenticDev '26)가 인기 절약 스킬의 효과를 정답 확인과 함께 재 보니 청구액이 안 변했다고 보고. 이걸 사용자 손에 쥐여 주는 도구가 없다.
- 차별점은 이 셋, 특히 1번. 토큰 계산기를 하나 더 만들면 열 번째 도구가 된다.

근거로 쓸 외부 결과(측정하는 사람들이 이미 보인 것):
- 비용 분산의 84%를 **턴 수**가 설명, 관찰 크기는 4% (TurnCost, POVC '26).
- 같은 모델에서 하네스에 따라 비용 최대 2~3배, 성공률 차이는 오차 범위 (HarnessTax, arXiv 2610.04433).
- 잘게 쪼갠 위임은 약 7배 토큰, 서브에이전트 fan-out은 1.4~5.9배 (실무 실측 다수, 난징대 preprint).

## 첫 탐침: Codex 한도 환율은 단순 회귀로 안 나온다 (confirmed, 2026-10-23)

- Codex rollout의 `token_count` 이벤트에는 요청마다 `rate_limits.primary.used_percent`(5시간 창)가 찍힌다.
- 사용률이 오를 때까지의 토큰을 종류별(캐시 안 된 입력·캐시 입력·출력)로 모아 회귀: 요청 485개 → 12개씩 묶음 93개.
- **R² = −0.7.** 단순 선형 모델로는 설명이 안 된다.
- 원인 후보 (hypothesis) — 그대로 설계 요구사항이 된다:
  1. 같은 계정의 다른 세션(다른 프로젝트·`codex exec`)이 같은 한도를 깎는다 → **계정 단위로 모든 rollout을 합쳐야** 한다.
  2. 사용률이 1% 단위 정수 → 요청 단위가 아니라 **한도 구간 단위**로 맞춰야 한다.
  3. 한도가 토큰이 아니라 모델·effort 가중 연산량일 수 있다 → **모델·effort를 변수**로.
- 확인 방법: 1~3을 반영해 재회귀. R²가 오르지 않으면 "Codex 환율은 관측 범위 표시만" 으로 후퇴.

### 재회귀 결과 (confirmed, 2026-10-24)

계정의 rollout 20개, 이벤트 5,576개(Plus, 2026-09-29~10-24)를 시간순으로 합쳐 5시간 창 40개로 나눴다.
스크립트 `~/.local/share/agent-usage-audit/codex_rate.py`, 보고서 같은 폴더 `reports/2026-10-24-codex-rate.md`.

| 회귀 | 검증 R² (min(LOO, 시간순 holdout)) | 판정 |
|---|---|---|
| 1%p 구간 단위 (lag 0·1) | −1.2 ~ −1.0 | 불가: Δ%가 거의 다 1이라 설명할 분산이 없다 |
| **5시간 창 단위** | **0.92** | **추정 가능** |
| 창 단위 + 모델·effort | −0.23 | 과적합 (드문 조합이 창 4~5개) |
| 주간 창 단위 | 0.29 | 불가 (창 11개) |

5시간 한도 1%p ≈ 캐시 안 된 입력 66K · 캐시 입력 742K · 출력 5.5K 토큰 (LOO fold 범위 56~76K / 717~810K / 4.9~6.2K).
즉 원인 후보 2(정수 구간)가 맞았고, 창 단위로 묶으니 풀렸다. 한계: 100%에서 잘린 창 7개, 시작부터 >0%인 창 4개.
비전과 분해 계산식은 `09-agent-health-vision.md`.

## 원칙·리스크

- **로컬 전용, 텔레메트리 없음** (ctxmeter 기존 원칙 유지). transcript 원문을 복사·색인하지 않는다(고객 정보가 섞인 세션이 있다).
- 문서에 없는 API(Claude 사용량 엔드포인트 등)는 쓰더라도 "비공식, 언제든 깨질 수 있음"을 결과 옆에 표시. 기본값은 끈다.
- Kiro 요금 FAQ: 외부 자동화 하네스로 Kiro 인터페이스 밖에서 요청을 보내는 것은 금지. 우리는 **로컬 로그를 읽기만** 하므로 해당 없음으로 본다(hypothesis — 배포 전 문구 재확인).
- 숫자의 출처를 항상 표시: 실측 / 추정 / 비공식.

## Open questions
